# Deployment-per-operator productization

We ship one codebase deployed once per operator company. Deployments differ by environment (`APP_URL`, `MAIL_FROM`, `DATABASE_URL`, `FUNCTIONAL_CURRENCY`, `MAP_TILES_URL`, shadow TTLs), by configured data (hubs, zones, pricing rules, delivery options), and by frontend skin, never by code forks. A solo driver-operator and a regional courier run identical binaries at different scales; the operator's customers see only the operator's brand because sender identity, domains, and map styles are deployment configuration. Provisioning follows a fixed ritual: provision box → migrate → bootstrap owner → invite staff → configure data → pin release.

We chose this over (a) multi-tenant SaaS now, which would force `tenantId` activation, a theming engine, and shared-infrastructure operations before any customer demands them (and would put our platform brand between couriers and their customers), and over (b) per-client code forks, which rot within one release cycle. It is hard to reverse because secrets, domains, and the isolation story assume per-deployment boundaries, and because every module is built to be consumed identically by any skin. It is surprising because one deployable serves both a two-man van operation and a multi-hub courier without structural change: scale differences are operational, not architectural. The `tenantId` seam stays dormant until operator-count economics justify shared infrastructure; activation criteria are deliberately unset.
