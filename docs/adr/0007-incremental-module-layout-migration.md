# Incremental module-layout migration with enforced barrels

The first four feature modules (auth, customers, merchants, locations, pricing) were built as flat top-level dirs (`src/auth`, `src/pricing`, ...) without barrels or boundary enforcement, drifting from ADR 0002's `src/modules/<domain>` layout. The cost surfaced concretely: the pricing module reached into shipment writes (its cancel route mutated `shipments.status` directly), violating ADR 0002's "one DB writer per dataset" rule.

From issue 07 onward, new modules live at `src/modules/<domain>/` and expose a public barrel `index.ts`; everything outside a module imports only that barrel, enforced by an ESLint `no-restricted-imports` rule scoped to `apps/api/src` (deep paths into `modules/*/*` are errors; the barrel is exempt). The shipments module is the first to follow it and is now the sole writer of `shipments.status` via its transition gateway. Legacy flat slices migrate opportunistically in future issues rather than in one big-bang refactor; until then, cross-module writes are prevented by convention and review, not lint, for the pre-07 modules. We chose incremental migration over (a) amending the spec to bless flat dirs, which would entrench the drift and lose boundary guarantees just as offline sync makes write-ownership safety critical, and over (b) a full refactor first, which pauses features on this constrained dev box for cosmetic moves. It's hard to reverse because every future module adopts the barrel contract and the sync module will call these public APIs. Known gap: relative cross-module deep imports inside `src/modules/**` are not yet caught by lint; closing that needs per-capture boundaries rules alongside the legacy migration.
